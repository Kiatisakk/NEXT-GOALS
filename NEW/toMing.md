# NEXT GOAL

## สรุปแนวคิดและงานที่ต้องทำต่อสำหรับหมิง

**โครงการ:** NEXT GOAL — ผู้ช่วยวางแผนเงินและเตือนความเสี่ยงก่อนโอนบน K PLUS  
**Track:** Data Science & Intelligence  
**กลุ่มเป้าหมาย:** First Jobbers อายุ 22–30 ปี  
**งานที่ต้องส่งก่อน:** One-Page Summary Pitch (PDF 1 หน้า) ครบ 5 หัวข้อตาม [Booklet.md](../OLD/Booklet.md) ส่วนสไลด์ใช้เตรียมรอบ Pitching Day

NEXT GOAL ช่วยตอบสองคำถามในจังหวะที่ผู้ใช้ต้องตัดสินใจ: **วันนี้ใช้เงินได้เท่าไรโดยไม่กระทบค่าใช้จ่ายจำเป็นและเป้าหมาย?** และ **การโอนเงินครั้งนี้จะทำให้แผนการเงินเสี่ยงหรือไม่?** ระบบเสนอทางเลือกที่คำนวณจากข้อมูลและสมมติฐานที่ตรวจสอบได้ พร้อมแสดงผลกระทบของแต่ละทางเลือกให้ผู้ใช้ตัดสินใจเอง

## 1. สิ่งที่โจทย์ต้องการและจุดต่างของ NEXT GOAL

[Booklet.md](../OLD/Booklet.md) ระบุให้เสนอฟีเจอร์สำหรับ K PLUS ที่ช่วย First Jobbers บริหารเงินและลดความเสี่ยงจาก Scam/Fraud โดย Track 2 ต้องแสดงบทบาทของ Data, Analytics หรือ Intelligence ในการตัดสินใจทางการเงิน

งานวิจัยใน [MingDeepResearch.md](../OLD/MingDeepResearch.md) ชี้ว่า K PLUS มีความสามารถด้านสรุปรายรับรายจ่ายและ e-Pocket อยู่แล้ว แนวคิดนี้จึงต่อยอดด้วย **การคำนวณผลของการตัดสินใจล่วงหน้า** เช่น ถ้าออมเพิ่ม ซื้อของชิ้นใหญ่ หรือโอนเงินก้อนหนึ่ง วันนี้และเดือนถัดไปจะยังจ่ายค่าใช้จ่ายจำเป็นและไปถึงเป้าหมายได้หรือไม่

NEXT GOAL มี 3 ส่วนที่เชื่อมกัน:

1. **Safe-to-Spend:** ประมาณวงเงินใช้จ่ายที่เหลือหลังกันค่าใช้จ่ายจำเป็น เงินสำรอง และเงินสำหรับเป้าหมายตามข้อมูลที่มี พร้อมบอกว่าส่วนใดเป็นข้อมูลยืนยันและส่วนใดเป็นค่าประมาณ
2. **Goal Planning:** เสนอหลายแผนการออมและเวลาถึงเป้าหมาย เมื่อรายรับหรือรายจ่ายเปลี่ยน ระบบคำนวณแผนใหม่และแสดงผลกระทบอย่างตรงไปตรงมา
3. **Transfer Check:** ก่อนโอนเงินที่เข้าข่ายเสี่ยง ระบบประเมินผลต่อเงินจำเป็นและแสดงคำเตือนเฉพาะบุคคล สัญญาณนี้เป็นส่วนหนึ่งของการประเมินความเสี่ยง ไม่ใช่หลักฐานว่าผู้รับเป็นมิจฉาชีพ

## 2. โครงสำหรับ One-Page Summary Pitch — งานส่งหลัก

ใช้ข้อความด้านล่างเป็นร่าง แล้วตัดให้พอดีหนึ่งหน้า PDF โดยคงหัวข้อทั้ง 5 ตามโจทย์

### 1) Problem Statement

First Jobbers อาจเห็นยอดเงินคงเหลือแต่ไม่เห็นเงินที่ต้องจ่ายในอีกหลายวันข้างหน้า เมื่อมีรายจ่ายก้อนใหญ่หรือคำชวนให้โอนเงิน การตัดสินใจครั้งเดียวอาจกระทบค่าใช้จ่ายจำเป็นและเป้าหมายการออม ข้อมูลจากการสำรวจระดับประเทศช่วยยืนยันความสำคัญของเงินสำรอง แต่ **ไม่ใช่สถิติเฉพาะกลุ่มอายุ 22–30 ปี**

### 2) Proposed Solution

NEXT GOAL ประมาณ Safe-to-Spend จากยอดเงิน รายรับที่คาดว่าจะเข้า ค่าใช้จ่ายประจำ และเงินสำรองที่ผู้ใช้กำหนด จากนั้นคำนวณแผนไปถึงเป้าหมายหลายทางเลือก เมื่อมีรายจ่ายเปลี่ยนแปลง ระบบเสนอแผนใหม่ ก่อนโอนเงินที่อาจกระทบค่าใช้จ่ายจำเป็น ระบบแสดงผลล่วงหน้า เช่น “หลังโอน 4,500 บาท เงินที่กันไว้จ่ายค่าเช่าในอีก 6 วันอาจไม่พอ” แล้วให้ผู้ใช้ตรวจสอบรายการอีกครั้ง

### 3) Target Users

คนเริ่มทำงานอายุ 22–30 ปีที่มีรายรับประจำหรือเพิ่งเริ่มสร้างประวัติธุรกรรม โดยเฉพาะผู้ที่ต้องจัดสรรค่าเช่า ค่าเดินทาง เงินสำรอง และเป้าหมายระยะกลางพร้อมกัน

### 4) Value Proposition

- **ผู้ใช้:** เห็นผลของการใช้เงินก่อนตัดสินใจ ปรับแผนเมื่อชีวิตเปลี่ยน และได้รับคำเตือนที่อธิบายด้วยข้อมูลการเงินของตนเอง
- **K PLUS:** เพิ่มคุณค่าจากข้อมูลธุรกรรมและ e-Pocket ที่มีอยู่ และทดลองวัดได้ว่าฟีเจอร์ช่วยให้ผู้ใช้วางแผนต่อเนื่องหรือทบทวนรายการโอนที่มีความเสี่ยงมากขึ้นเพียงใด ผลทางธุรกิจต้องประเมินจากการทดลองจริง

### 5) Track Perspective — Data Science & Intelligence

ใช้การตรวจจับรายรับ/รายจ่ายประจำและการประมาณกระแสเงินสดร่วมกับ **finite-horizon dynamic programming (DP)** เพื่อเลือกแผนออมหลายเป้าหมายภายใต้ข้อจำกัดค่าใช้จ่ายจำเป็นและเงินสำรอง เมื่อข้อมูลเปลี่ยน ระบบคำนวณนโยบายใหม่จากสถานะปัจจุบัน ความไม่แน่นอนแสดงเป็นช่วงผลลัพธ์หรือสถานการณ์จำลอง ส่วนคำเตือนก่อนโอนใช้ผลกระทบต่อกระแสเงินสดประกอบกับสัญญาณธุรกรรมที่มีสิทธิ์ใช้และตรวจสอบได้

## 3. POC ที่ทำและพิสูจน์ได้

### ข้อมูลเข้าและสมมติฐาน

- ยอดเงินที่ใช้ได้ รายรับและวันที่คาดว่าจะได้รับ ค่าใช้จ่ายประจำ หนี้ที่ต้องชำระ และเป้าหมายที่ผู้ใช้ตั้ง
- ผู้ใช้ตรวจและแก้รายรับ/รายจ่ายที่ระบบอนุมานได้ โดยเฉพาะกรณีเพิ่งเริ่มใช้ K PLUS หรือมีธุรกรรมน้อย
- แยก **ข้อมูลจริง**, **ค่าที่ผู้ใช้กรอก**, และ **ค่าประมาณ** ในหน้าผลลัพธ์ หากข้อมูลยังไม่พอ ให้แสดงช่วงคาดการณ์แทนตัวเลขที่ดูแม่นยำเกินจริง
- วงเงินใช้จ่ายจำเป็นขั้นต่ำและเพดานภาระหนี้เป็น **สมมติฐานของ POC ที่ปรับได้** ไม่อ้างว่า DSR/DTI 40% เป็นเกณฑ์บังคับของ ธปท. เพราะ ธปท. ระบุว่าไม่ได้กำหนดเพดาน DSR กลางสำหรับการปล่อยสินเชื่อ ([ธปท.](https://www.bot.or.th/th/research-and-publications/articles-and-publications/articles/article-2024nov25.html))

### วิธีคำนวณ

1. ประมาณกระแสเงินสด **ตามวันครบกำหนด** โดยแยกรายรับที่ยืนยันแล้วกับรายรับที่คาดการณ์ กันค่าใช้จ่ายจำเป็นและเงินสำรองตามที่ผู้ใช้เลือกก่อนคำนวณ Safe-to-Spend; ตรวจทุกวันในช่วงที่แสดงผล ไม่ใช้เพียงยอดสิ้นเดือน
2. ใช้ **finite-horizon DP** วางแผนรายเดือนในช่วงทดลอง 1–24 เดือนสำหรับเป้าหมาย 2–3 รายการ เริ่มจากเดือนสุดท้ายแล้วย้อนกลับมาเลือกการจัดสรรเงินที่ให้ผลดีที่สุดภายใต้ข้อมูลและข้อจำกัดของ POC
3. ในแต่ละสถานะ ตัดทางเลือกที่ทำให้เงินจ่ายรายการจำเป็นในวันครบกำหนดไม่พอ แล้วให้คะแนนจากลำดับความสำคัญของเป้าหมาย ระยะเวลาที่เลื่อน และเงินใช้จ่ายที่เหลือ แสดง 2–3 แผนที่มีข้อแลกเปลี่ยนต่างกัน
4. เมื่อมีธุรกรรมใหม่ ใช้ยอดเงินจริงเป็นสถานะเริ่มต้นและคำนวณ DP ใหม่ แสดงว่าเงินใช้ได้และวันถึงเป้าหมายเปลี่ยนเท่าไร **ไม่รับประกันว่าเป้าหมายเดิมจะคงอยู่เสมอ**

ขนาดปัญหาและเวลาในการประมวลผลขึ้นกับจำนวนตัวเลือก ความละเอียดของจำนวนเงิน และข้อมูลที่ต้องดึง จึงยังไม่ระบุว่า “มีเพียงไม่กี่พันเส้นทาง” หรือ “เสร็จใน <5 ms” จนกว่าจะมีผล benchmark ของ POC

### แปลงงานวิจัย DP เป็น NEXT GOAL

งานของ [Das, Ostrov, Radhakrishnan และ Srivastav (ฉบับวารสาร 2022)](https://doi.org/10.1016/j.jbankfin.2021.106192) ใช้ DP เลือกว่าจะทำเป้าหมายใดและจัดพอร์ตอย่างไรเมื่อทรัพยากรมีจำกัด แนวคิดที่ NEXT GOAL นำมาใช้คือ **ตัดสินใจหลายช่วงเวลาและจัดลำดับหลายเป้าหมายร่วมกัน** โดยเปลี่ยนตัวเลือกจากพอร์ตลงทุนเป็นการออม การใช้เงิน และการเลื่อนรายจ่ายที่ผู้ใช้เลือกได้ [Franklin Templeton GOE](https://www.franklintempleton.com.au/articles/2025/multi-asset/inside-the-goals-optimization-engine) เป็นตัวอย่างการนำ DP ไปใช้กับระบบวางแผนตามเป้าหมาย แต่ไม่ใช่หลักฐานว่า NEXT GOAL มีผลลัพธ์หรือประสิทธิภาพเท่ากัน

| ส่วนของ DP ใน POC | นิยามที่ใช้ |
| --- | --- |
| **สถานะ (state)** | เดือนปัจจุบัน เงินสดที่ยังใช้ได้ เงินสำรอง และความคืบหน้าของแต่ละเป้าหมาย โดยยอดเงินแต่ละส่วนต้องไม่ถูกนับซ้ำ |
| **ทางเลือก (action)** | จำนวนเงินที่กันให้แต่ละเป้าหมายในเดือนนั้น การลดหรือเลื่อนเป้าหมายที่ยืดหยุ่นได้ และวงเงินใช้จ่ายที่ผู้ใช้ยอมรับ |
| **การเปลี่ยนสถานะ (transition)** | นำรายรับเข้าและหักบิลตามวันจริงของเดือน แล้วหักหรือเพิ่มเงินตามทางเลือกที่เลือก; ใช้สถานการณ์รายรับ/รายจ่ายหลายแบบเมื่อมีข้อมูลรองรับ |
| **ข้อจำกัด (constraints)** | ไม่ให้แผนปกติจ่ายค่าใช้จ่ายจำเป็นไม่พอในวันครบกำหนด คงเงินสำรองขั้นต่ำที่ผู้ใช้เลือก และไม่สร้างภาระหนี้ใหม่โดยปริยาย หากไม่มีแผนที่ผ่าน ให้บอกว่าต้องปรับอะไร |
| **คะแนน (objective)** | ให้ค่าน้ำหนักตามความสำคัญของเป้าหมายและการถึงเป้าหมายทันเวลา พร้อมหักคะแนนเมื่อเงินใช้จ่ายตึงตัวหรือเป้าหมายถูกเลื่อน; น้ำหนักเป็นสมมติฐานที่ต้องให้ผู้ใช้ตรวจและปรับได้ |
| **ผลลัพธ์ (policy)** | แผนว่าในแต่ละสถานะควรกันเงินเท่าไรและเป้าหมายใดควรเลื่อน พร้อมผลต่อ Safe-to-Spend; เมื่อตัวเลขจริงเปลี่ยน ให้คำนวณนโยบายใหม่ |

หัวใจของ DP คือคำนวณ `V(เดือน, สถานะ) = ค่าสูงสุดของ [คะแนนจากทางเลือกเดือนนี้ + V(เดือนถัดไป, สถานะใหม่)]` โดยพิจารณาเฉพาะทางเลือกที่ผ่านข้อจำกัด แล้วบันทึกทางเลือกที่ดีที่สุดของแต่ละสถานะไว้ เมื่อเกิดรายการโอนหรือรายจ่ายใหม่ ให้นำยอดจริงเข้าเป็นสถานะใหม่และอ่านแผนจากนโยบายที่คำนวณใหม่ สำหรับ POC เริ่มด้วยกระแสเงินสดคาดการณ์หนึ่งชุดและทดสอบแผนกับหลายสถานการณ์; หากมีข้อมูลเพียงพอจึงเพิ่มความน่าจะเป็นของรายรับ/รายจ่ายลงในการคำนวณ DP

แนวคิดเงินออมเป็นกันชนภายใต้ข้อจำกัดการกู้ยืมจาก [Deaton (1991)](https://www.nber.org/papers/w3196) ใช้อธิบายเหตุผลของเงินสำรองในโมเดล ส่วนงาน [Merton (1969)](https://doi.org/10.2307/1926560) และ [Merton (1971)](https://doi.org/10.1016/0022-0531(71)90038-X) เป็นรากฐานการตัดสินใจใช้เงินและลงทุนข้ามเวลา แต่ POC นี้ยังไม่แนะนำสัดส่วนสินทรัพย์ลงทุน จึงไม่อ้างว่าใช้โมเดลพอร์ตของ Merton โดยตรง

**ขอบเขตการพิสูจน์:** DP ให้คำตอบดีที่สุดเฉพาะภายในสถานะ ทางเลือก คะแนน ข้อจำกัด และความละเอียดจำนวนเงินที่กำหนดไว้ ไม่การันตีอนาคตจริง ใช้การจำลองสถานการณ์หรือ Monte Carlo **ทดสอบแผนหลังคำนวณ** เมื่อมีสมมติฐานความไม่แน่นอนที่สมเหตุสมผล และเทียบผลกับกฎออมแบบคงที่ก่อนกล่าวว่า DP ช่วยได้มากกว่า สคริปต์ทดลองใน `OLD` ยังไม่ใช่หลักฐานความเหมาะที่สุดของโมเดลนี้ เพราะยังไม่ได้จำลองการจ่ายเพื่อเป้าหมายหลายรายการและตัดทิ้งบางเส้นทางตามยอดเงินสะสม

### POC ที่ทำได้แล้ว

มีต้นแบบ Python แบบ command line ใน [`next_goal_dp.py`](next_goal_dp.py) และคำอธิบายวิธีรัน/รูปแบบข้อมูลใน [`DP_POC_README.md`](DP_POC_README.md) โดยใช้ stochastic Bellman DP จริง: คำนวณค่าคาดหมายจากหลายสถานการณ์ เก็บ policy ของแต่ละสถานะ เดิน forward เพื่อรายงานโอกาสเป้าหมายอยู่ที่ 0/50/100% และมี Transfer Check สำหรับเปรียบเทียบก่อนกับหลังโอน

รันตรวจสอบด้วย `python -m unittest discover -s NEW -p "test_*.py"` ผลล่าสุดผ่าน 9 เคส ครอบคลุมการเลือก Bellman, เหตุการณ์ตามวัน, เงินที่กันให้เป้าหมาย, การเลื่อนเป้าหมาย, แผนที่ไม่ผ่านสภาพคล่อง, การรวมความน่าจะเป็น, กฎออมคงที่สำหรับเปรียบเทียบ และการโอน 4,500 บาทใน demo ข้อมูลทั้งหมดเป็นข้อมูลสังเคราะห์ จึงยังไม่ควรใช้ตัวเลขจาก demo เป็นผลการทดลองกับลูกค้าจริง

### คำเตือนก่อนโอน

Transfer Check ตรวจผลของรายการต่อค่าใช้จ่ายจำเป็นที่กำลังจะถึงกำหนด และอาจใช้สัญญาณอื่น เช่น ผู้รับใหม่หรือยอดโอนผิดไปจากปกติ **หากมีข้อมูลและสิทธิ์ใช้อย่างเหมาะสม** ผลลัพธ์คือคำเตือนพร้อมเหตุผลและตัวเลือกให้ทบทวน ไม่กล่าวหาผู้รับว่าเป็นบัญชีม้า และไม่อ้างว่าตรวจจับสแกมได้ทุกกรณี

ตัวอย่างคำเตือน: “หากโอน 4,500 บาทตอนนี้ เงินที่กันไว้สำหรับค่าเช่าในอีก 6 วันอาจไม่พอ กรุณาตรวจสอบผู้รับและเหตุผลในการโอนอีกครั้ง”

ข้อจำกัดที่ต้องพูดตรง ๆ: การโอนให้คนรู้จักอาจทำให้เงินจำเป็นไม่พอโดยไม่ใช่สแกม ขณะเดียวกันการโอนให้มิจฉาชีพอาจไม่ทำให้เงินจำเป็นขาด ระบบจึงต้องทดสอบทั้ง **false positive** และเคสสแกมที่ไม่เข้าเงื่อนไขสภาพคล่อง

## 5. โครงสไลด์สำหรับ Pitching Day

ทำหลังจาก One-Page Pitch ลงตัวแล้ว สไลด์ควรสั้นและใช้ demo หนึ่งสถานการณ์เชื่อมทุกส่วน

1. **NEXT GOAL:** หนึ่งประโยคอธิบายปัญหาและคุณค่า
2. **ปัญหา:** ยอดเงินคงเหลือไม่บอกค่าใช้จ่ายที่รออยู่ พร้อมข้อมูล ธปท. และ AOC ที่ระบุช่วงอายุถูกต้อง
3. **วิธีใช้:** ตั้งเป้าหมาย → เห็น Safe-to-Spend → เลือกแผน
4. **Data Science:** แสดง state → action → ข้อจำกัด → ผลลัพธ์ของ DP พร้อมข้อมูลเข้าและสมมติฐาน
5. **Demo เมื่อแผนสะดุด:** รายจ่ายใหม่เข้ามา แล้วระบบแสดงผลต่อวันถึงเป้าหมายและเงินใช้จ่าย
6. **Demo ก่อนโอน:** แสดงผลต่อค่าใช้จ่ายจำเป็นและคำเตือน โดยไม่กล่าวหาว่าเป็นสแกมที่ยืนยันแล้ว
7. **ผลทดสอบและข้อจำกัด:** ความถูกต้องของ forecast, false positive และเวลา benchmark ที่วัดได้จริง
8. **คุณค่าต่อผู้ใช้และ K PLUS:** สิ่งที่คาดว่าจะดีขึ้นและวิธีทดลองพิสูจน์

## 6. คำถามที่ควรเตรียมตอบ

**Q: ทำไมใช้ DP และทำไมไม่ให้ LLM คำนวณแผน?**  
A: DP เหมาะกับการเลือกการจัดสรรเงินหลายเดือนและหลายเป้าหมาย โดยระบุสถานะ ทางเลือก และข้อจำกัดให้ตรวจซ้ำได้ LLM อาจช่วยอธิบายผลภายหลัง แต่ตัวเลขหลักมาจาก DP และการประมาณกระแสเงินสด ส่วนความแม่นยำของข้อมูลเข้าและ forecast ยังต้องวัด ไม่รับประกันว่าผลลัพธ์ถูกต้อง 100%

**Q: ลูกค้าใหม่มีข้อมูลน้อย จะเริ่มอย่างไร?**  
A: ให้ผู้ใช้ระบุวันรับเงิน ค่าใช้จ่ายจำเป็น และเป้าหมายขั้นต่ำก่อน ระบบแสดงผลเป็นค่าประมาณและขอให้ตรวจยืนยันข้อมูล เมื่อมีประวัติเพิ่มจึงปรับประมาณการ ไม่สมมติว่าลูกค้าทุกคนมี payroll หรือประวัติบิลตั้งแต่วันแรก

**Q: คำเตือนจะรบกวนการโอนปกติหรือไม่?**  
A: มีโอกาส จึงต้องออกแบบเกณฑ์เตือน ทดลองกับเคสโอนปกติและเคสเสี่ยง แล้วรายงาน false positive พร้อมให้ผู้ใช้ตรวจสอบเหตุผลของคำเตือน การประเมินสภาพคล่องเป็นเพียงหนึ่งสัญญาณ ไม่ใช่ตัวพิสูจน์สแกม
